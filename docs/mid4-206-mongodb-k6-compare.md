# MID4-206 활동내역 조회 성능 테스트 결과

## 이 문서가 답하는 질문

이 문서는 `GET /api/user-activities/{userId}` 활동내역 조회 API가 현재 RDB(PostgreSQL) 구조에서 어느 정도까지 버티는지 정리한다.

이번 작업의 목적은 MongoDB Read Model을 바로 적용하는 것이 아니라, 나중에 MongoDB를 붙였을 때 같은 조건으로 비교할 기준선을 만드는 것이다. 그래서 RDB 기준으로 일반 조회, 높은 요청량, 데이터가 한곳에 몰린 상황, 삭제/취소 데이터가 많은 상황, 읽기와 쓰기가 섞인 상황을 각각 확인했다.

## 한눈에 보는 결론

| 질문 | 답 |
| --- | --- |
| 평소 수준의 활동내역 조회는 괜찮은가 | 괜찮다. 50 VU 10분, 100 VU 10분 모두 통과했다. |
| RDB만으로 초당 요청을 얼마나 버티는가 | 190 rps 30분은 통과했다. 250 rps 10분도 수치는 통과했지만 DB CPU가 높아 보수적으로 봐야 한다. |
| 장시간 높은 부하에서 한계가 보였는가 | 300 rps 10분은 실패했다. 지연 시간과 dropped iterations가 기준을 넘었다. |
| 특정 글이나 관심사에 데이터가 몰리면 어떤가 | 10 rps 10분만 통과했다. 20 rps부터 p95 기준을 넘어서 MongoDB Read Model 또는 쿼리 최적화 후보로 봐야 한다. |
| 삭제된 댓글/기사/사용자를 걸러내는 비용은 어떤가 | 50 rps 1분은 통과했지만 50 rps 10분은 p95 기준을 넘었다. |
| 조회 중 댓글 작성, 좋아요, 구독 변경이 섞여도 괜찮은가 | 현재 Outbox 미구현 RDB 기준에서는 80/20, 50/50 혼합 부하가 통과했다. |
| MongoDB 성능 비교까지 끝났는가 | 아니다. MongoDB Read Model 구현과 전환 설정이 준비된 뒤 같은 조건으로 다시 측정해야 한다. |

## 읽기 전에 알아둘 말

| 용어 | 쉬운 의미 |
| --- | --- |
| VU | 동시에 접속해 API를 호출하는 가상의 사용자 수 |
| RPS | 1초에 보내는 요청 수 |
| p95 | 요청 100개 중 느린 쪽 5개를 제외했을 때의 응답 시간 |
| p99 | 요청 100개 중 가장 느린 1개 근처의 응답 시간 |
| dropped iterations | k6가 목표한 요청을 제때 만들지 못해 빠뜨린 횟수 |
| error rate | 실패한 HTTP 요청 비율 |
| checks rate | 응답 구조 검증이 통과한 비율 |
| fan-out | 특정 글, 댓글, 관심사 하나에 조회, 좋아요, 구독 같은 관계 데이터가 많이 몰린 상태 |
| soak | 짧게 한 번 보는 것이 아니라 같은 부하를 오래 유지해 보는 테스트 |
| mixed | 조회 요청과 쓰기 요청을 섞어 실제 사용 상황에 가깝게 보는 테스트 |

## 테스트 종류

| 이름 | 이 테스트로 확인한 것 |
| --- | --- |
| 시동 확인 테스트(smoke) | 스크립트, 인증, 응답 구조가 정상인지 먼저 확인한다. |
| 일반 사용량 테스트(average) | 평소처럼 여러 사용자가 동시에 조회해도 빠른지 확인한다. |
| 높은 사용량 테스트(high-load) | 사용자가 더 많아졌을 때도 응답이 버티는지 확인한다. |
| 한계 테스트(stress) | 사용자를 단계적으로 늘리며 어느 지점부터 느려지는지 확인한다. |
| 초당 요청 수 테스트(throughput) | 1초에 정해진 요청 수를 계속 보낼 때 서버가 따라오는지 확인한다. |
| 장시간 유지 테스트(soak) | 통과한 부하를 오래 유지해도 계속 안정적인지 확인한다. |
| 데이터 몰림 테스트(fan-out) | 한 댓글, 기사, 관심사에 관계 데이터가 많이 몰렸을 때 느려지는지 확인한다. |
| 삭제/취소 데이터 테스트(exclusion) | 삭제된 댓글/기사/사용자를 제외하면서 조회할 때 비용이 커지는지 확인한다. |
| 읽기/쓰기 혼합 테스트(mixed) | 조회 중 댓글 작성, 좋아요, 기사 조회, 구독 변경이 섞여도 괜찮은지 확인한다. |

## 환경과 합격 기준

측정은 로컬 dev 애플리케이션과 Docker Postgres 기준으로 수행했다. 데이터는 `SEED_SCALE=10m` 기준으로 새로 적재했다.

| 항목 | 값 |
| --- | --- |
| 대상 API | `GET /api/user-activities/{userId}` |
| 기본 사용자 | `00000001-0000-4000-8000-000000000001` |
| 사용자 분산 확인 | 단일 사용자, 2명 round-robin, 5명 round-robin |
| 기본 로그 조건 | `dev-sql-warn` |
| 처리량 테스트 VU 한도 | `preAllocatedVUs=500`, `maxVUs=500` |
| 통과 기준 | 실패율 1% 미만, 응답 검증 99% 초과, dropped 0, p95 200ms 미만, p99 500ms 미만 |

Postgres CPU는 k6 컨테이너 CPU를 더한 값이 아니다. Docker CPU 표기 기준이라 100%를 넘을 수 있고, 문서의 CPU 값은 대부분 실행 중 특정 시점의 스냅샷이다. 그래서 통과/실패는 CPU보다 p95, p99, 실패율, dropped iterations를 우선한다.

## 테스트별 결과 요약

### 1. 일반 조회는 통과

평소 사용량과 높은 사용량을 가정한 조회는 기준을 만족했다.

| 테스트 | 부하 | 시간 | p95 | p99 | 판단 |
| --- | --- | --- | ---: | ---: | --- |
| 일반 사용량 | 50 VU | 10분 | 31.19ms | 47.88ms | 통과 |
| 높은 사용량 | 100 VU | 10분 | 38.76ms | 67.89ms | 통과, timeout warning 10건 관찰 |
| 한계 테스트 | 50 -> 100 -> 200 -> 400 VU | 각 3분 | 101.35ms | 186.74ms | 통과, timeout warning 14건 관찰 |

기본 활동내역 조회는 100 VU 10분까지 안정적으로 볼 수 있다. 다만 timeout warning이 관찰됐기 때문에 운영 기준값으로 바로 확정하기보다는 비교 기준선으로 사용한다.

### 2. 초당 요청 수는 190 rps 장시간 통과

RDB 기준에서 190 rps 30분은 통과했다. 250 rps 10분도 수치상 통과했지만 Postgres CPU가 높게 관찰되어 여유가 충분하다고 보기는 어렵다.

| 테스트 | 부하 | 시간 | p95 | p99 | dropped | 판단 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 반복 측정 평균 | 200 rps | 1분, 3회 | 24.30ms | 30.49ms | 0 | 통과 |
| 반복 측정 평균 | 250 rps | 1분, 3회 | 26.63ms | 34.30ms | 0 | 통과, CPU 70% 전후 |
| 반복 측정 평균 | 300 rps | 1분, 3회 | 55.63ms | 92.92ms | 0 | 통과, CPU 100% 초과 스냅샷 포함 |
| 장시간 유지 | 190 rps | 30분 | 37.29ms | 52.11ms | 0 | 통과 |
| 장시간 유지 | 250 rps | 10분 | 49.41ms | 136.01ms | 0 | 수치 통과, CPU 82.73% 관찰 |
| 장시간 유지 | 300 rps | 10분 | 1,692.74ms | 1,934.22ms | 1,159 | 실패 |

현재 문서화된 보수적 장시간 통과 구간은 190 rps다. 250 rps 이상은 MongoDB Read Model 비교 또는 RDB 쿼리 최적화의 대상으로 남긴다.

### 3. 데이터 몰림 상황은 RDB에서 빠르게 한계가 보임

특정 댓글, 기사, 관심사에 관계 데이터가 몰리도록 만든 뒤 조회했다. 이 테스트는 전체 데이터 수보다 “한 대상에 얼마나 몰렸는지”를 보기 위한 것이다.

| 몰림 대상 | 추가한 데이터 |
| --- | ---: |
| 최근 댓글 10개 | 댓글마다 좋아요 1,000개 |
| 최근 조회 기사 10개 | 기사마다 댓글 1,000개 |
| 최근 조회 기사 10개 | 기사마다 조회 사용자 10,000명 |
| 구독 관심사 50개 | 관심사마다 구독자 1,000명 |
| 편중 관심사 1개 | 구독자 50,000명 추가 |

| 부하 | 시간 | p95 | p99 | dropped | 판단 |
| --- | --- | ---: | ---: | ---: | --- |
| 10 rps | 1분 | 165.68ms | 196.45ms | 0 | 통과 |
| 10 rps | 10분 | 164.37ms | 187.57ms | 0 | 통과 |
| 20 rps | 1분 | 228.66ms | 281.29ms | 0 | 실패, p95 초과 |
| 30 rps | 1분 | 11,951.05ms | 12,270.91ms | 0 | 실패, 응답 시간 급증 |
| 40 rps | 1분 | 19,662.55ms | 20,367.61ms | 468 | 실패 |
| 50 rps | 1분 | 21,448.99ms | 22,445.07ms | 1,161 | 실패 |

결론은 명확하다. 일반 데이터에서는 RDB가 충분히 빠르지만, 관계 데이터가 특정 대상에 몰리면 현재 쿼리는 20 rps부터 기준을 넘는다.

## RDB에서 먼저 검토할 작은 개선안

이번 fan-out 문제는 API를 여러 번 호출해서 생긴 문제가 아니다. 한 SQL 안에서 좋아요, 조회, 구독 같은 관계 row를 세는 동안 `users`, `comments`, `articles`의 삭제 여부를 반복해서 확인하는 구조가 문제다.

이 문제를 줄이는 가장 작은 RDB 개선안은 관계 row에 현재 노출 상태를 두는 것이다.

| 상태 | 의미 |
| --- | --- |
| `ACTIVE` | 현재 화면과 카운트에 포함해도 되는 상태 |
| `USER_DELETED` | 관련 사용자가 삭제되어 현재 노출하면 안 되는 상태 |
| `COMMENT_DELETED` | 관련 댓글이 삭제되어 현재 노출하면 안 되는 상태 |
| `ARTICLE_DELETED` | 관련 기사가 삭제되어 현재 노출하면 안 되는 상태 |

이렇게 두면 조회 쿼리는 매번 사용자, 댓글, 기사 테이블을 조인해서 삭제 여부를 확인하지 않고 `status = 'ACTIVE'`만 확인할 수 있다.

```sql
SELECT COUNT(*)
FROM comment_likes
WHERE comment_id = :commentId
  AND status = 'ACTIVE';
```

```sql
SELECT COUNT(*)
FROM subscriptions
WHERE interest_id = :interestId
  AND status = 'ACTIVE';
```

이 상태는 단순한 성능용 컬럼만은 아니다. “삭제된 사용자, 삭제된 댓글, 삭제된 기사와 연결된 활동을 현재 사용자 화면과 카운트에 포함할 것인가”라는 비즈니스 기준을 저장한 값으로 볼 수 있다.

이번 작은 개선 범위는 복구 처리가 아니라 삭제 이벤트 시점의 노출 상태 갱신이다. 상태 갱신은 현재 `ACTIVE`인 row에만 적용한다.

예를 들어 사용자 삭제 시에는 사용자와 연결된 `ACTIVE` row만 `USER_DELETED`로 바꾼다. 댓글 삭제 시에는 댓글과 연결된 `ACTIVE` row만 `COMMENT_DELETED`로 바꾸고, 기사 삭제 시에는 기사와 연결된 `ACTIVE` row만 `ARTICLE_DELETED`로 바꾼다.

이미 `USER_DELETED`, `COMMENT_DELETED`, `ARTICLE_DELETED` 상태인 row는 다른 삭제 이벤트에서 덮어쓰지 않는다. 이 기준을 두면 단일 status 안에서 상태 간 높고 낮음을 따지지 않아도 되고, 각 도메인 작업도 독립적으로 작게 나눌 수 있다.

복구 처리는 이번 범위에서 제외한다. 복구까지 포함하면 기존 삭제 원인을 다시 계산해야 하므로 작업 범위가 커진다.

따라서 이 개선은 MongoDB 적용 없이도 RDB에서 작게 검토할 수 있는 후보로 남긴다. 특히 `subscriptions`, `comment_likes`, `article_views`, `comments`처럼 카운트와 활동내역 조회에 반복 사용되는 관계 테이블부터 효과를 확인하는 것이 좋다.

### 4. 삭제/취소 데이터가 많으면 오래 버티는 구간에서 흔들림

삭제된 댓글, 삭제된 기사, 삭제된 사용자 구독 데이터가 많은 상황을 만들고, 조회 시 제외 조건 비용을 확인했다.

| 제외 데이터 | 추가량 |
| --- | ---: |
| target user의 최신 삭제 댓글 | 10,000건 |
| 최신 좋아요 대상 삭제 댓글 | 10,000건 |
| 최신 조회 대상 삭제 기사 | 10,000건 |
| target user 구독 관심사의 삭제 사용자 구독 | 50,000건 |

| 부하 | 시간 | p95 | p99 | dropped | 판단 |
| --- | --- | ---: | ---: | ---: | --- |
| 10 rps | 1분 | 107.89ms | 123.09ms | 0 | 통과 |
| 20 rps | 1분 | 119.60ms | 146.44ms | 0 | 통과 |
| 30 rps | 1분 | 134.35ms | 163.87ms | 0 | 통과 |
| 40 rps | 1분 | 142.15ms | 182.72ms | 0 | 통과 |
| 50 rps | 1분 | 188.02ms | 223.08ms | 0 | 통과 |
| 50 rps | 10분 | 228.00ms | 279.56ms | 0 | 실패, p95 초과 |

삭제/취소 데이터 조건은 fan-out보다 급격한 실패는 아니지만, 오래 유지하면 p95 기준을 넘었다. 단기 결과만 보고 안전하다고 판단하면 안 된다.

### 5. 읽기/쓰기 혼합 부하는 현재 RDB 기준 통과

조회만 하는 테스트와 달리, 댓글 작성, 좋아요, 기사 조회 기록, 구독 변경을 섞어 실행했다. 현재 Outbox 구현은 없는 상태이므로 결과 용도는 `rdb-mixed-no-outbox`다.

| 비율 | 부하 | 시간 | 전체 HTTP RPS | p95 | p99 | 판단 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 읽기 80%, 쓰기 20% | 5 VU | 1분 | 5.68 | 32.61ms | 54.21ms | 통과 |
| 읽기 80%, 쓰기 20% | 50 VU | 10분 | 57.26 | 30.55ms | 52.60ms | 통과 |
| 읽기 80%, 쓰기 20% | 100 iter/s | 1분 | 118.03 | 23.59ms | 30.03ms | 통과 |
| 읽기 80%, 쓰기 20% | 150 iter/s | 1분 | 175.87 | 22.09ms | 26.58ms | 통과 |
| 읽기 50%, 쓰기 50% | 100 iter/s | 1분 | 133.53 | 19.95ms | 23.84ms | 통과 |

쓰기 요청이 DB 상태를 바꾸므로 공식 측정은 각 시나리오 직전에 10m seed를 새로 적재한 결과만 직접 비교 대상으로 본다. Outbox가 구현되면 같은 조건으로 다시 측정해야 한다.

## 로그 조건을 나눈 이유

처음에는 개발 중 SQL을 직접 확인하기 위해 `dev-default-debug` 조건으로 실행했다. 이 조건은 SQL 출력이 많아서 테스트가 길어지거나 요청량이 커질 때 로그 I/O가 성능에 영향을 줄 수 있다.

최종 판단에는 `dev-sql-warn`을 사용한다. 이 조건은 dev profile은 유지하되 SQL/배치 로그만 `warn`으로 낮춘 상태다. 운영 환경과 완전히 같은 조건은 아니지만, SQL DEBUG/TRACE 출력의 영향을 제거한 RDB 비교 기준으로 사용한다.

서로 다른 로그 조건의 결과는 직접 비교하지 않는다. `dev-default-debug` 결과는 동작 확인용 참고값이고, 최종 처리량 판단은 `dev-sql-warn` 결과를 우선한다.

## 실행 방법

RDB 기본 조회를 확인한다.

```powershell
.\scripts\performance\activity-history\k6\run-mongodb-compare.ps1 `
  -Variant rdb `
  -Scenario baseline
```

RPS 기준 처리량을 확인한다.

```powershell
.\scripts\performance\activity-history\k6\run-mongodb-compare.ps1 `
  -Variant rdb `
  -Scenario throughput `
  -Rates 200,250,300 `
  -Duration 1m
```

읽기/쓰기 혼합 부하를 확인한다.

```powershell
.\scripts\performance\activity-history\k6\run-mongodb-compare.ps1 `
  -Variant rdb `
  -K6Script mixed `
  -MixRatio 80/20 `
  -Scenario average
```

MongoDB Read Model을 적용한 뒤에는 애플리케이션 전환 설정을 먼저 맞추고 같은 명령에서 `-Variant mongo`로 반복한다.

## 후속 작업

- MongoDB Read Model 구현 후 같은 데이터와 같은 k6 조건으로 RDB/MongoDB 결과를 비교한다.
- Outbox 구현 후 읽기/쓰기 혼합 부하를 같은 조건으로 다시 측정한다.
- fan-out 조건에서 관계 row 노출 상태 컬럼 도입, 카운트 집계 방식 변경, MongoDB Read Model 비교를 검토한다.
- 250 rps 이상 구간은 DB CPU 여유가 충분하지 않으므로 운영 기준으로 확정하기 전에 별도 환경에서 재측정한다.
